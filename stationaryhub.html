The system at a glance

One inventory. Multiple orders.

The central challenge is keeping stock consistent when orders access the same warehouse inventory.

01 — The problem

Stock is easy to track until orders overlap.

An inventory system needs to track available products and handle requests for different quantities. The problem becomes more interesting when multiple orders are processed concurrently.

If two threads inspect and update the same stock without suitable coordination, they can interfere with one another. An order may appear to have enough stock when another order has already claimed it.

The goal

Apply object-oriented programming and concurrency concepts to organise inventory, represent orders and protect shared stock updates.

↳

The key question: how can the system prevent conflicting stock updates while still allowing orders to be processed by separate threads?

02 — Design

Separate responsibilities.

The class design separates products, orders and warehouse operations so that each part has a clear responsibility.

Reflection

What this project taught me.

Concurrent programming requires more than starting multiple threads. Shared data needs clear ownership rules, and operations that modify that data need to be coordinated.

The project also reinforced the value of separating responsibilities across classes. A clearer design makes it easier to reason about what an operation should do and where its behaviour belongs.

My next step is to validate the behaviour with repeatable tests, especially cases where multiple orders request the last available units of a product.
